# Sprint 10 — Active Directory Security Integration

## Overview

This sprint integrated an existing Python Active Directory Security Monitor with the SOC Home Lab Wazuh deployment.

The goal was not to replace native Windows Security Event Logs. Instead, the custom monitor was integrated as an additional structured telemetry source that enriches Active Directory security monitoring.

The integration demonstrates how a custom security tool can be connected to a centralized SIEM while preserving native Windows audit logs as the primary forensic evidence source.

## Objectives

- Validate that the Windows Security Event Log is enabled on the Domain Controller.
- Confirm that native Windows Security events are collected by Wazuh.
- Review and reuse the existing Python AD Security Monitor.
- Export monitor alerts as structured JSON Lines telemetry.
- Configure the Wazuh Agent to collect the custom JSONL log.
- Create and validate a Wazuh detection rule for domain account creation.
- Perform a controlled and reversible Active Directory test.
- Document the investigation and rollback process.

## Native Windows Security Log Validation

The Domain Controller Security Event Log was validated before integrating the custom monitor.

```powershell
Get-WinEvent -ListLog Security |
Select-Object LogName, IsEnabled, RecordCount, MaximumSizeInBytes
```

The Security log was enabled and contained recent events.

Native Windows Security telemetry was also confirmed in the Wazuh archive index:

```text
agent.name: WIN-SERVER-DC
data.win.system.channel: Security
decoder.name: windows_eventchannel
```

## Custom Monitor Integration

The existing Python monitor generates human-readable Active Directory security alerts in:

```text
C:\AD-Monitor\logs\alerts.log
```

A separate exporter was created to convert monitor alerts into JSON Lines:

```text
C:\AD-Monitor\wazuh_export.py
```

The exporter writes structured events to:

```text
C:\AD-Monitor\logs\wazuh-ad-monitor.jsonl
```

Example JSONL event:

```json
{
  "integration": "ad-security-monitor",
  "schema_version": "1.0",
  "event_id": 4720,
  "event_name": "Usuário criado",
  "event_type": "account_created",
  "severity": "HIGH",
  "target_user": "soc.test.example",
  "actor": "Administrator"
}
```

## Wazuh Agent Collection

The following configuration was added to the Windows Wazuh Agent configuration:

```xml
<localfile>
  <log_format>json</log_format>
  <location>C:\AD-Monitor\logs\wazuh-ad-monitor.jsonl</location>
</localfile>
```

This allowed the Wazuh Agent to collect structured telemetry from the custom monitor and forward it to the Wazuh Manager.

## Detection Engineering

A custom Wazuh rule was created to detect domain account creation events generated by the custom monitor.

| Field | Value |
|---|---|
| Rule ID | `100240` |
| Rule Level | `10` |
| Event ID | `4720` |
| Detection | Domain user account creation |
| MITRE ATT&CK | `T1136.002` — Create Account: Domain Account |

```xml
<rule id="100240" level="10">
  <if_sid>86600</if_sid>
  <field name="integration">^ad-security-monitor$</field>
  <field name="event_id">^4720$</field>
  <description>AD Security Monitor: domain user account created</description>
  <group>ad_monitor,account_creation,windows,</group>
  <mitre>
    <id>T1136.002</id>
  </mitre>
</rule>
```

The rule was validated with `wazuh-logtest` before deployment.

## Controlled Validation

A controlled Active Directory account creation test was executed using the existing test automation.

```powershell
.\generate-test-alerts.ps1 -Test AccountChanges
```

The test created a temporary account using the `soc.test.*` naming pattern.

The following chain was validated:

```text
Windows Security Event ID 4720
        ↓
Python AD Security Monitor
        ↓
JSONL exporter
        ↓
Wazuh Agent
        ↓
Wazuh JSON decoder
        ↓
Wazuh Rule 100240
        ↓
Wazuh Alert
```

## Detection Decision

Event ID `4738` was observed during testing but was not promoted to an individual Wazuh alert.

Account modification events can be generated frequently during normal account operations and test workflows. Alerting on every `4738` would create unnecessary noise.

The sprint prioritized Event ID `4720` because domain account creation is a high-confidence security event with direct relevance to identity persistence and unauthorized account creation.

## Rollback

The test account was temporary and removed automatically by the test script.

Manual validation command:

```powershell
Get-ADUser -Filter "SamAccountName -like 'soc.test.*'"
```

If a test account remains:

```powershell
Remove-ADUser -Identity <test-account> -Confirm:$false
```

## Key Takeaways

- Native Windows Security Event Logs remain the primary source of evidence.
- Custom tools can enrich SIEM visibility without replacing native telemetry.
- JSON Lines is a practical format for structured SIEM ingestion.
- Wazuh Agent localfile collection can integrate custom endpoint telemetry.
- Detection rules should prioritize high-confidence events and avoid noisy alerting.
- Domain account creation was successfully detected and mapped to MITRE ATT&CK `T1136.002`.
